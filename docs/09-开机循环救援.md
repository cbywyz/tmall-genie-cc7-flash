# 09 · 开机循环救援（system_server 崩溃时怎么救）

这是本仓库最有价值的一篇：**设备卡在开机 logo、WiFi adb 完全失联、USB adb 长期 `offline`** 时的无损修复方法。

## 先明确一件事：这时候不用刷机

关键事实：

> **这台设备的 `adbd` 和 Magisk 的 root，在 `system_server` 启动之前就已就绪。**

所以即使框架层死循环，你依然能进 root shell 做手术。**不需要 recovery，不需要 BROM，不需要恢复出厂。**

## 现象对照

| 层面 | 表现 | 含义 |
|---|---|---|
| 屏幕 | 卡在开机 logo 不动 | 框架没起来 |
| `getprop sys.boot_completed` | 空 | 系统未完成启动 |
| `getprop init.svc.bootanim` | `running` | 开机动画还在跑（说明 zygote 在，但 AMS 挂了） |
| WiFi adb | 连不上 | 网络栈依赖框架 |
| USB adb | 设备列出但 `offline` 或能进 shell 但 `cmd package` 报 `Can't find service: package` | adbd 活着，框架服务没注册 |

## 第一步：取证（别瞎猜）

```bash
adb shell su -c 'ls -t /data/system/dropbox/ | head -10'
adb shell su -c 'head -40 /data/system/dropbox/system_server_crash@*.txt'
```

典型的崩溃签名：

```
Process: system_server
java.lang.NullPointerException: ...
    at com.android.server.am.ActivityRecord.<init>(ActivityRecord.java:808)
    at com.android.server.am.ActivityStarter.startHomeActivityLocked(ActivityStarter.java:647)
    at com.android.server.am.ActivityManagerService.systemReady(ActivityManagerService.java:14815)
```

看到 `startHomeActivityLocked` + `applicationInfo` 空指针 = **有 HOME 候选包被挂起/禁用了**。

## 第二步：手术（5 条命令）

```bash
adb shell su
```

进入 root shell 后：

```sh
# 1. 停框架，防止 system_server 重启时用内存态覆盖我们的修改
stop zygote

# 2. 备份原始状态文件
cp /data/system/users/0/package-restrictions.xml /data/local/tmp/pr.orig.xml

# 3. 去掉所有挂起标记
sed 's/ suspended="true"//g' /data/local/tmp/pr.orig.xml > /data/local/tmp/pr.fixed.xml

# 4. 原地写回
cat /data/local/tmp/pr.fixed.xml > /data/system/users/0/package-restrictions.xml

# 5. 校验后重启
grep -c 'suspended="true"' /data/system/users/0/package-restrictions.xml   # 必须为 0
sync
reboot
```

### 三个关键细节（踩过的坑）

| 细节 | 为什么 |
|---|---|
| 先 `stop zygote` | 否则 `system_server` 一重启就把内存状态写回文件，改了个寂寞 |
| 用 `cat >` 原地覆盖 | `cat` 打开目标文件截断写入，**保留 inode / 属主 / SELinux 上下文**。用 `mv`、`adb push` 或 `sed -i` 新建文件会变成 `root:root` + 错误上下文，`system_server` 读不了 |
| 只用 `sed` 去掉 `suspended="true"` | 不要整个文件重写，保留原有结构（`<preferred-activities>`、`<enabled-components>` 等） |

### 预期纠正时间

从发现问题到开机完成：**约 8 分钟**（含一次重启）。

## 第三步：验证

```bash
adb shell getprop sys.boot_completed          # 1
adb shell dumpsys window | grep mCurrentFocus # 正常桌面
```

## 附：另一种「假故障」—— 触摸完全失灵

## 现象

系统已经起来了（能进桌面），但**滑动、点击全部无响应**，看起来像触摸屏坏了。

## 定位

```bash
adb shell dumpsys window | grep mCurrentFocus
```

如果输出是某个阿里 HOME：

```
mCurrentFocus=Window{... com.alibaba.ailabs.genie.children/com.alibaba.ailabs.genie.launcher.activity.AdultHomeActivity}
```

再配合：

```bash
adb shell cat /proc/loadavg      # load 20+，说明有进程在空转
adb shell top -n 1 -b | head -12
```

看到 `genie.children` 占 50% CPU —— 结论：**前台窗口僵死，把触摸事件全吞了**，不是触摸层的问题。

## 处置

```bash
adb shell am force-stop com.alibaba.ailabs.genie.children
adb shell am start -n com.dangbei1.tvlauncher/com.dangbei.launcher.ui.main.MainActivity
```

触摸立刻恢复。

> **关于长期方案**：曾经用 [§08 的开机脚本](08-系统优化-冻结预装.md) 在开机后强拉第三方桌面来绕开这个僵死窗口，后来**撤掉了** —— 那个卡死是系统刚做完 dexopt、负载 20+ 时的暂时现象，不是日常状态；为它长期养一个第三方桌面，反而盖住原生功能（取舍详见 §08）。
> 现在的做法：**回归原桌面，不做任何开机干预**。实测重启后 10s / 30s / 60s 均稳定停在 `AdultHomeActivity`，触摸链路正常（`input tap` 能唤醒屏保并回桌面），logcat 无 `Input dispatching timed out`。
> 若偶尔再遇到卡死，手动执行上面两行即可，不必常驻脚本。

## 附：什么情况下才真的需要 BROM / 恢复出厂

| 情况 | 处理 |
|---|---|
| `system_server` 崩、adbd 还活着 | ✅ 本文方法，root shell 修 `/data` |
| `system` 分区写坏、`adbd` 起不来 | BROM 写回 `backup/system.bin` |
| `boot` 选错架构、黑屏 | BROM 写回 `backup/boot.bin` |
| `nvram` 损坏、WiFi 打不开 | BROM 写回 `backup/nvram.bin` |
| 只想清空用户数据 | `adb shell su -c 'stop zygote'` 后 BROM 擦 `userdata`，或恢复出厂 |

**顺序原则：能用 root shell 解决的，绝不刷分区；能只刷一个分区的，绝不整盘回滚。**
